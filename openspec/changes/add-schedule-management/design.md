# Design

## Context

См. `proposal.md` — Why. Проект использует FastAPI, SQLite из стандартной библиотеки и
Jinja2. Валидация общая для HTML и API находится в `app/models.py`, SQL и транзакции — в
`app/repository.py`. Время хранится в UTC, ввод и отображение — в МСК (UTC+3). Текущая
схема имеет версию 1 и не содержит рабочих интервалов; существующие слоты созданы заранее.

## Goals / Non-Goals

**Goals:**

- Добавить рабочий интервал как отдельную сущность, чтобы проверять пересечения даже в
  перерыве, где слотов нет.
- Сохранить существующие данные и добавить обновление схемы с версии 1 до версии 2.
- Использовать одну модель валидации и один метод репозитория для HTML и API.
- Выполнять проверку пересечений и вставку интервала со слотами в одной транзакции.

**Non-Goals:**

- Редактирование и удаление уже добавленных интервалов.
- Перенос записей пациентов и отмена слотов.
- Поддержка интервалов через полночь и разных часовых поясов.
- Отдельный интерфейс для управления справочником врачей.

## Decisions

- **Отклонять время, не кратное 30 минутам.** Это проще и предсказуемее, чем создавать
  только полные слоты: пользователь сразу видит, что интервал нужно исправить, а в базе не
  появляются частичные или неожиданно обрезанные слоты. Альтернатива — молча создавать
  полные слоты — скрывает потерю введённого времени.
- **Хранить рабочий интервал в таблице `schedule_intervals`.** Проверка только по слотам
  не заметила бы новый интервал внутри перерыва. Отдельная таблица делает перерыв частью
  занятого времени и позволяет запретить такое пересечение. Альтернатива — хранить только
  слоты — дешевле, но нарушает требование о непересекающихся интервалах.
- **Проверять и интервалы, и слоты.** Старые базы версии 1 содержат слоты без интервалов;
  проверка по слотам сохраняет запрет пересечений и для них.
- **Обновлять схему через идемпотентный `CREATE TABLE IF NOT EXISTS` и `PRAGMA
  user_version = 2`.** Для добавления новой таблицы этого достаточно, существующие таблицы
  и данные не пересоздаются. База с версией больше 2 не открывается.
- **Одна транзакция `BEGIN IMMEDIATE`.** Она сериализует добавление расписания с записью
  пациента и не даёт двум запросам одновременно пройти проверку пересечений.
- **Общая модель `ScheduleCreate`.** Она проверяет кратность, порядок времени, границы
  перерыва и наличие хотя бы одного слота. HTML-форма и API используют её без дублирования
  правил.

## Risks / Trade-offs

- **Существующие слоты без интервалов.** Их нельзя проверить как интервалы, но проверка по
  слотам не даёт создать пересекающееся расписание. → Проверяем обе таблицы.
- **Интервал через полночь не поддерживается.** Пользователь получит ошибку «окончание
  должно быть позже начала». → Это явное ограничение; при необходимости его можно
  расширить отдельной задачей.
- **Даты на границе `datetime.min`.** Перевод МСК в UTC может выйти за границы типа. →
  Ошибка обрабатывается и возвращается как конфликт с понятным сообщением.
- **Часовой пояс в API.** Время с `tzinfo` отклоняется, чтобы не перепутать локальное и
  абсолютное время. → API принимает местное время без часового пояса, как и форма.

## Migration Plan

1. При старте приложение читает `PRAGMA user_version`.
2. Если версия больше 2, запуск прекращается.
3. Иначе выполняется идемпотентная схема: создаётся `schedule_intervals` и её индекс,
   затем устанавливается версия 2.
4. Существующие таблицы, слоты, пациенты и записи не изменяются. Откат не требуется:
   новая таблица не влияет на старые запросы.
