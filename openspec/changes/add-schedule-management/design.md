# Design

## Context

См. `proposal.md`. Приложение — FastAPI, Jinja2 и SQLite без JavaScript и сборки фронтенда. Слоты уже хранятся в UTC и отображаются в фиксированном UTC+3; у таблицы `slots` есть уникальность `(doctor_id, starts_at)`. Схема базы в этом изменении не меняется.

## Goals / Non-Goals

**Goals:**

- Добавить серверную страницу создания расписания, работающую без JavaScript.
- Переиспользовать общие правила валидации для HTML-формы и будущего API.
- Гарантировать атомарность: либо создаётся весь интервал, либо ничего.
- Не изменять существующие слоты и записи пациентов.

**Non-Goals:**

- Редактирование и удаление уже созданных слотов.
- Массовое создание расписания на несколько дней или врачей.
- Новый JSON API для управления расписанием: в этом изменении только HTML-страница.
- Изменение схемы SQLite и миграция данных.

## Decisions

### Двухшаговый выбор поликлиники и врача

Страница `GET /schedule/manage` показывает форму выбора поликлиники. После отправки этой формы страница перезагружается с `clinic_id` и показывает только врачей выбранной поликлиники, а также основную форму создания.

Альтернатива — один список всех врачей с подписью поликлиники — отклонена: она противоречит требованию «врач выбранной поликлиники» и позволяет отправить несогласованную пару. JavaScript не используется, поэтому перезагрузка страницы — самый простой надёжный вариант.

### Общая модель `ScheduleCreate` в `app/models.py`

Модель принимает `clinic_id`, `doctor_id`, `date`, `start_time`, `end_time`, `break_start`, `break_end`. Проверки кратности, порядка границ, положения перерыва и прошедшего времени выполняются в модели, чтобы HTML и будущий API использовали одни правила. Проверка принадлежности врача поликлинике и пересечений требует базы и выполняется в репозитории.

Альтернатива — валидация только в обработчике формы — отклонена: проект требует общих правил в `app/models.py`.

### Отклонение вместо обрезки при шаге не 30 минут

Если интервал или перерыв не выровнены по получасу, форма возвращает ошибку. Альтернатива «создавать только полные слоты» отклонена: она молча меняет введённые пользователем границы и затрудняет объяснение результата.

### Отклонение всего интервала при пересечении

Репозиторий ищет любые существующие слоты врача, пересекающиеся с новым интервалом, и при находке отменяет всю операцию. Сообщение перечисляет конфликтующие интервалы в МСК.

Альтернативы — пропускать совпадающие слоты или создавать только свободные — отклонены: частичное создание усложняет понимание результата и маскирует ошибку ввода. Требование «не должно быть пересекающихся интервалов» трактуется строго.

### Атомарное создание в одной транзакции

`ClinicRepository.create_slots()` открывает `BEGIN IMMEDIATE`, проверяет существование поликлиники и врача, принадлежность врача поликлинике, затем пересечения и вставляет все слоты. Уникальный индекс `(doctor_id, starts_at)` остаётся страховкой от гонки. Существующие строки не обновляются и не удаляются.

### Время и дата

Дата и время формы трактуются как московские (UTC+3), затем переводятся в UTC для хранения. Проверка «в прошлом» сравнивает первый слот с текущим моментом UTC. Интервал не может пересекать полночь, так как окончание обязано быть позже начала в пределах одной даты.

### Перенаправление после успеха

После создания выполняется `303` на `/?clinic_id=<id>&date=<YYYY-MM-DD>&notice=slots-created`. Страница расписания показывает подтверждение. Это исключает повторную отправку формы при обновлении страницы.

## Risks / Trade-offs

- **Одновременное создание двумя регистраторами** → `BEGIN IMMEDIATE` сериализует проверку и вставку, а уникальный индекс откатывает гонку; второй запрос получит понятную ошибку пересечения.
- **Очень длинный интервал создаёт много слотов** → максимум 48 слотов в сутки при шаге 30 минут; отдельный лимит не нужен.
- **Строгий отказ при любом пересечении** → регистратор не может «дополнить» частично совпадающий интервал; зато результат предсказуем, а сообщение показывает конфликтующие слоты.
- **Ошибки валидации в двух местах** → модель отвечает за ввод, репозиторий за состояние базы; тесты покрывают оба уровня.

## Migration Plan

Схема не меняется, `PRAGMA user_version` остаётся равным 1. Существующая база продолжает работать без миграции; откат — удаление нового маршрута и шаблона, данные не затрагиваются.
