# Spec Delta

## Purpose

Позволяет регистратору добавлять рабочие интервалы врачей и получать готовые получасовые
слоты для записи пациентов без ручного изменения базы.

## ADDED Requirements

### Requirement: Создание рабочего интервала

Система SHALL позволять указать поликлинику, врача этой поликлиники, дату, начало и
окончание рабочего интервала, а также необязательный перерыв.

#### Scenario: Интервал без перерыва

- **WHEN** регистратор указывает поликлинику, врача, дату 01.12.2026 и интервал 09:00–11:00
- **THEN** система создаёт рабочий интервал и четыре получасовых слота

#### Scenario: Интервал с перерывом

- **WHEN** регистратор указывает интервал 09:00–11:00 и перерыв 09:30–10:00
- **THEN** система создаёт слоты 09:00–09:30, 10:00–10:30 и 10:30–11:00

### Requirement: Получасовые слоты

Система MUST делить рабочий интервал на полные слоты по 30 минут и не создавать слоты
внутри перерыва. Созданные слоты SHALL появляться в существующем расписании и быть
доступными для записи, если их время ещё не прошло.

#### Scenario: Созданные слоты видны в расписании

- **WHEN** рабочий интервал успешно добавлен
- **THEN** его слоты отображаются в расписании выбранной поликлиники на эту дату
- **AND** свободные будущие слоты доступны для записи пациента

### Requirement: Кратность 30 минутам

Система MUST отклонять рабочий интервал, если начало, окончание или границы перерыва
не кратны 30 минутам. Частичные слоты не создаются.

#### Scenario: Некратное время

- **WHEN** регистратор указывает начало 09:15
- **THEN** система не создаёт слоты
- **AND** форма объясняет, что время должно быть кратно 30 минутам

#### Scenario: Некратный перерыв

- **WHEN** регистратор указывает перерыв 10:15–10:45
- **THEN** система не создаёт слоты и объясняет ошибку

### Requirement: Корректность интервала и перерыва

Система MUST требовать, чтобы окончание было позже начала, перерыв был указан обеими
границами, находился внутри рабочего интервала и не занимал его целиком.

#### Scenario: Окончание раньше начала

- **WHEN** регистратор указывает интервал 11:00–09:00
- **THEN** система отклоняет ввод и объясняет, что окончание должно быть позже начала

#### Scenario: Перерыв вне интервала

- **WHEN** регистратор указывает интервал 09:00–11:00 и перерыв 10:30–12:00
- **THEN** система отклоняет ввод и объясняет, что перерыв должен находиться внутри интервала

#### Scenario: Указана только одна граница перерыва

- **WHEN** регистратор заполняет начало перерыва, но не заполняет окончание
- **THEN** система отклоняет ввод и просит указать обе границы или оставить обе пустыми

### Requirement: Врач выбранной поликлиники

Система MUST проверять, что выбранный врач относится к выбранной поликлинике.

#### Scenario: Врач из другой поликлиники

- **WHEN** регистратор выбирает поликлинику №01 и врача из поликлиники №02
- **THEN** система не создаёт расписание и объясняет, что врач не работает в этой поликлинике

### Requirement: Запрет пересекающихся интервалов

Система MUST запрещать новый рабочий интервал, если он пересекается с уже добавленным
интервалом врача, включая перерыв этого интервала. Соседние интервалы разрешены.

#### Scenario: Пересечение с существующим интервалом

- **WHEN** у врача уже есть интервал 09:00–11:00
- **AND** регистратор добавляет интервал 10:00–12:00
- **THEN** система не создаёт новый интервал и объясняет пересечение

#### Scenario: Пересечение с перерывом

- **WHEN** у врача уже есть интервал 09:00–11:00 с перерывом 09:30–10:00
- **AND** регистратор добавляет интервал 09:30–10:00
- **THEN** система не создаёт новый интервал и объясняет пересечение

#### Scenario: Соседние интервалы

- **WHEN** у врача уже есть интервал 09:00–11:00
- **AND** регистратор добавляет интервал 11:00–13:00
- **THEN** система создаёт новый интервал и его слоты

### Requirement: Сохранение существующих данных

Система MUST добавлять новые интервалы и слоты, не изменяя существующие слоты, записи
пациентов и медицинские карты.

#### Scenario: Существующая запись сохраняется

- **WHEN** пациент уже записан на приём, а регистратор добавляет другое расписание
- **THEN** существующая запись и её слот остаются без изменений

### Requirement: Обновление схемы базы

Система MUST обновлять базу версии 1 до версии 2 при старте, добавляя таблицу рабочих
интервалов без потери существующих данных.

#### Scenario: Обновление базы версии 1

- **WHEN** приложение запускается с базой версии 1, содержащей слоты и записи
- **THEN** схема становится версией 2
- **AND** существующие слоты и записи сохраняются

### Requirement: Единые правила для HTML и API

Система MUST применять одинаковые правила валидации и пересечений к HTML-форме и JSON API.

#### Scenario: Ошибка API

- **WHEN** клиент отправляет в `POST /api/schedules` интервал с некратным временем
- **THEN** API возвращает ошибку 422 и не создаёт слоты

#### Scenario: Пересечение через API

- **WHEN** клиент отправляет в `POST /api/schedules` пересекающийся интервал
- **THEN** API возвращает ошибку 409 и не создаёт слоты

### Requirement: Понятные ошибки формы

Система MUST объяснять причину ошибки формы и сохранять введённые значения, чтобы
регистратор мог исправить только проблемное поле.

#### Scenario: Ошибка сохраняет ввод

- **WHEN** регистратор отправляет форму с началом 09:15
- **THEN** страница показывает объяснение ошибки
- **AND** введённое значение 09:15 остаётся в поле
