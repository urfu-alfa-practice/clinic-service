# Design

## Context

Мотивация и объём — в `proposal.md`, поведение — в `specs/schedule-management/spec.md`. Здесь только технические решения.

Текущее состояние, важное для подхода:

- Слоты уже лежат в таблице `slots` (`doctor_id`, `starts_at`, `ends_at`), время хранится в UTC строкой ISO, отображение — МСК.
- `UNIQUE (doctor_id, starts_at)` защищает только точный дубль; пересечения по времени на уровне БД не запрещены.
- Бронирование уже использует `BEGIN IMMEDIATE` и проверку пересечений в Python/SQL (`repository.book`).
- Валидация HTML и API общая и живёт в `app/models.py`; HTML-ошибки переводит `field_errors` в `app/web.py`.
- JavaScript в проекте нет, интерфейс — обычные формы с GET/POST и ответом 303.
- Схема версионируется через `PRAGMA user_version`, механизма миграций нет.

## Goals / Non-Goals

**Goals:**

- Добавить страницу управления расписанием без изменения схемы БД.
- Переиспользовать существующие правила времени, валидации и транзакций.
- Сделать генерацию слотов и проверку пересечений детерминированными и тестируемыми.

**Non-Goals:**

- Удаление и редактирование слотов, несколько перерывов, расписание на диапазон дат.
- Новый JSON API (по решению пользователя — только HTML-страница).
- Триггеры и миграции для защиты пересечений на уровне БД.
- Авторизация и роли: страница, как и остальные, доступна локально без входа.

## Decisions

### 1. Схема БД не меняется

Новые слоты вставляются в существующую `slots`. Перерыв — это только входной параметр генерации, хранить его не нужно: по требованиям важны созданные слоты, а не исходный интервал.

Альтернативы: таблица `work_intervals` с последующей материализацией слотов — отклонено, усложняет модель и требует миграции без выгоды для задачи.

### 2. Валидация формы — в `app/models.py`

Новая Pydantic-модель (`WorkIntervalCreate`) с полями `clinic_id`, `doctor_id`, `date`, `start_time`, `end_time`, `break_start`, `break_end`. Проверки формы, не зависящие от БД:

- границы интервала и перерыва: минуты `00` или `30`, секунды `0`;
- начало интервала раньше окончания;
- перерыв задан либо полностью, либо не задан;
- перерыв не выходит за границы интервала и начинается раньше, чем заканчивается;
- интервал даёт хотя бы один полный слот вне перерыва.

Сообщения — на русском, через `ValueError` в `model_validator`, чтобы HTML и будущий API получили одинаковые правила. `field_errors` расширяется обработкой ошибок уровня формы (ключ `__form__`), которые выводятся над полями.

Альтернатива: валидировать всё в обработчике `web.py` — отклонено, это разошлось бы с правилом проекта «общая валидация в models.py».

### 3. Проверка врача и пересечений — в репозитории, в одной транзакции

`repository.create_schedule(data)`:

1. `BEGIN IMMEDIATE`.
2. Проверяет, что врач существует и принадлежит выбранной поликлинике (иначе `NotFoundError`/`ConflictError`).
3. Читает существующие слоты врача, пересекающиеся с интервалом, и сравнивает их с каждым сгенерированным слотом.
4. При любом пересечении или совпадении — `ConflictError` с указанием конфликтующего интервала, ни одной вставки.
5. Иначе `executemany` по всем слотам и коммит.

Проверка и вставка под `BEGIN IMMEDIATE` сериализует одновременные запросы, как уже сделано для бронирования. Сравнение идёт по сгенерированным слотам, а не по всему интервалу: существующий слот внутри перерыва не мешает созданию, потому что новый слот на это время не появляется.

Альтернативы: `INSERT` по одному с откатом при ошибке — тот же результат, но больше кода; триггер в БД — требует миграции и выходит за объём.

### 4. Генерация слотов

Сетка якорится на начало интервала с шагом 30 минут. Кандидат `[t, t+30)` включается, если `t+30 <= end` и он не пересекается с перерывом `[break_start, break_end)`. Все границы уже выровнены валидацией, поэтому достаточно сравнения получасовых интервалов.

Дата и время формы трактуются как МСК: `datetime.combine(date, time, LOCAL_TIMEZONE)`, затем перевод в UTC существующим `timestamp()`.

### 5. Интерфейс без JavaScript: двухшаговая форма

Страница `/schedule/manage`:

- GET-панель выбора поликлиники (как на главной) перезагружает страницу с `clinic_id`;
- POST-форма содержит скрытый `clinic_id`, список врачей только выбранной поликлиники, дату и четыре поля времени.

Смена поликлиники сбрасывает зависимые поля — это ожидаемо, потому что меняется список врачей. Ссылка «Управление расписанием» добавляется на страницу расписания.

Альтернативы: один список всех врачей с группировкой по поликлиникам — проще, но нарушает требование «врач выбранной поликлиники»; зависимые списки на JavaScript — противоречит отсутствию JS в проекте.

### 6. Ответы и ошибки

- Успех: 303 на `/schedule/manage?...&notice=created` с числом созданных слотов; повторное обновление ничего не создаёт.
- Ошибка валидации: 422, сообщение и сохранённые значения (как в форме пациента).
- Конфликт: 409 с текстом, называющим существующий интервал.
- Не найден врач или поликлиника: 404.

### 7. Прошедшие даты разрешены

Требование не запрещает подготовку расписания задним числом; созданные в прошлом слоты просто не будут доступны для записи — это уже существующее правило `Slot.is_available`. Дополнительных ограничений не вводим.

## Risks / Trade-offs

- **Пересечения защищены только кодом.** Прямая запись в БД в обход репозитория может создать пересечение → при появлении второго писателя понадобится триггер и миграция; сейчас фиксируем это как осознанное ограничение.
- **`BEGIN IMMEDIATE` и таймаут 5 секунд.** При большом числе одновременных регистраторов возможен `database is locked` → для учебного локального приложения приемлемо; при необходимости увеличить `timeout`.
- **Длинный интервал даёт много слотов.** Максимум ограничен сутками (до 48 слотов) → отдельный лимит не вводим.
- **Смена поликлиники сбрасывает введённые поля.** Осознанный компромисс ради работы без JavaScript.
- **Дублирование логики пересечений.** Проверка похожа на проверку пересечений пациента, но не идентична (слоты против записей) → общий помощник не выделяем, чтобы не усложнять.

## Migration Plan

Миграция не требуется: схема и `PRAGMA user_version` не меняются. Откат — удалить маршруты, шаблон и ссылку; созданные слоты остаются в БД и не ломают существующее поведение.
