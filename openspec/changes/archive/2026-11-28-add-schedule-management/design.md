# Design

## Context

См. `proposal.md` → Why. Сервис — FastAPI-приложение с одной SQLite-базой; каждый запрос открывает короткое соединение в `ClinicRepository`. Таблица `slots` уже хранит произвольные интервалы и имеет `UNIQUE (doctor_id, starts_at)`; `book()` показывает образец атомарной проверки через `BEGIN IMMEDIATE`. Время хранится в UTC помощником `timestamp()`, а отображается в фиксированном UTC+3 фильтрами Jinja2. HTML-страницы серверные, без JavaScript. Миграций схемы нет, `PRAGMA user_version` равен 1.

## Goals / Non-Goals

**Goals:**

- Одна модель ввода и один набор ошибок для HTML-формы и API.
- Переиспользовать существующие обработчики `NotFoundError`, `ConflictError`, `ValidationError` и стиль транзакций.
- Добавлять слоты атомарно, не изменяя существующие слоты и записи пациентов.
- Не менять схему базы и демонстрационное наполнение.
- Покрыть поведение тестами, включая некорректный ввод и параллельные запросы.

**Non-Goals:**

- Редактирование и удаление уже созданных слотов, перенос записей.
- Авторизация, роли и аудит действий регистратора.
- Динамические списки на JavaScript, новые фронтенд-зависимости и CDN.
- Поддержка нестандартной длительности приёма и интервалов через полночь.
- Изменение правил записи пациента и демонстрационных данных.

## Decisions

1. **Общая модель ввода.** В `app/models.py` добавляется модель `ScheduleCreate(InputModel)` с полями `clinic_id`, `doctor_id`, `day`, `start_time`, `end_time` и необязательными `break_start`, `break_end`. Валидаторы проверяют формат `HH:MM`, шаг 30 минут, `end > start`, пару границ перерыва и его расположение внутри интервала, а также что интервал ещё не начался по МСК. HTML и API используют одну и ту же модель; `field_errors()` в `app/web.py` дополняется понятными сообщениями для новых полей. Альтернатива — отдельные схемы формы и API — отклонена: правила неизбежно разойдутся.

2. **Атомарная операция репозитория.** В `app/repository.py` добавляется `add_schedule(data) -> list[Slot]`. В одной транзакции `BEGIN IMMEDIATE` проверяются существование поликлиники, принадлежность врача к ней и пересечение с уже имеющимися слотами врача (`starts_at < новый_конец AND ends_at > новое_начало`). Затем вставляются все слоты интервала. Нарушение `UNIQUE (doctor_id, starts_at)` преобразуется в `ConflictError`. Альтернатива — сначала вставить, а потом удалить конфликтующие слоты — отклонена: она задевала бы существующие данные.

3. **Строгое выравнивание.** Все границы должны быть кратны 30 минутам; при нарушении отклоняется весь ввод. Частичное создание «только целых слотов» отклонено по решению пользователя: молчаливое игнорирование минут удивило бы регистратора.

4. **Только будущее.** Дата не может быть раньше `local_today()`, а начало интервала — раньше текущего момента. Сравнение идёт в UTC; пользовательский ввод трактуется как МСК. Разрешение прошедших дат отклонено по решению пользователя.

5. **HTML-страница без JavaScript.** Новый обработчик `GET/POST /schedule/manage` и шаблон `schedule_form.html`; ссылка добавляется в навигацию `base.html`. Поликлиника выбирается отдельным `<select>`, врачи выводятся в одном `<select>` с группами `<optgroup>` по поликлиникам; принадлежность врача проверяется на сервере. Успех даёт `303` на расписание с уведомлением о числе слотов; ошибки возвращают страницу формы со статусом `422`/`404`/`409`, конкретным сообщением и сохранёнными значениями. Варианты с динамическим списком на JavaScript и двухшаговым выбором через GET отклонены: первый нарушает принцип работы без JS, второй добавляет лишний переход.

6. **API.** `POST /api/slots` принимает ту же модель, возвращает `201` со списком созданных слотов и заголовок `Location` на расписание. Неизвестные поля отклоняются уже настройкой `InputModel`; ошибки валидации дают `422`, неизвестные поликлиника/врач — `404`, пересечение — `409`. Возврат только идентификаторов отклонён: спецификация требует видимых созданных слотов.

7. **Часовой пояс.** Границы интервала собираются как `datetime.combine(day, time, LOCAL_TIMEZONE)` и переводятся в UTC перед записью. Существующие `list_slots()` и Jinja-фильтры уже показывают слоты в МСК, поэтому отдельный слой отображения не нужен.

8. **Схема не меняется.** Новых колонок и таблиц нет, `PRAGMA user_version` остаётся равным 1; демо-наполнение не трогается. Это убирает риск потери данных при обновлении существующей базы.

## Risks / Trade-offs

- [Пересечение с отменёнными приёмами] → Проверка идёт по слотам, а не по активным записям, поэтому слоты с отменёнными приёмами тоже участвуют в запрете пересечений и остаются нетронутыми.
- [Два параллельных запроса] → `BEGIN IMMEDIATE` сериализует изменение; второй запрос видит уже созданные слоты и получает `ConflictError`, а уникальный индекс служит дополнительной страховкой.
- [Большой интервал] → В пределах одной календарной даты максимум 48 получасовых слотов, отдельного ограничения размера не требуется.
- [Ввод времени с секундами или неверный формат] → Серверный валидатор принимает только `HH:MM`/`HH:MM:SS` с нулевыми секундами и минутами, кратными 30; браузерные атрибуты `step`/`required` считаются подсказкой, а не проверкой.
- [Экранирование пользовательского текста] → Остаётся включённым автоматическое экранирование Jinja2; новые шаблоны не используют `|safe`.
- [Откат после выкатки] → Достаточно вернуть предыдущий код: база остаётся совместимой, а созданные слоты остаются корректными записями.

## Migration Plan

Изменений схемы и версии базы нет. Развёртывание — замена кода приложения; откат — возврат предыдущей версии кода. Обязательно проверять сценарий с уже существующей базой, созданной до этой версии.
